# CoreDrive RX v1.13.0

Region discovery asked one repeater per minute for a whole commute and got one answer
back. The cause was not the radio: the single in-flight request slot was never released
when a repeater stayed silent, and since that slot also gates the event-driven ask, the
first unanswered request disabled the path that exists for a moving receiver. Every ask
after it came from the 60-second timer, aimed at a candidate a clock had picked from the
whole session pool — which at road speed is a repeater you have already driven past.
This release frees that slot, and adds forwarders as a candidate source.

## What's new

- **A silent repeater no longer costs you every later ask.** A request now expires
  instead of holding the in-flight slot forever. The slot was released on a FLOOD
  send-ack, on an accepted reply and on disconnect — none of which is what actually
  happens on the road, where a request sent DIRECT to a repeater now behind you is
  simply never answered. Expiry is swept by the one-second tick rather than a timer,
  because the app is routinely backgrounded mid-drive and a `setTimeout` there fires
  late or not at all.

  A field log made the shape of it plain: 23 minutes, ~19 repeaters heard, every ask
  landing exactly on the timer cadence, not one event-driven ask, one reply.

- **Forwarders are asked too, not only nodes that answer a discover sweep.** A packet
  heard over a FLOOD route names its last hop, and that hop is the node that transmitted
  to us — one radio hop away, which is the direct-neighbour relation a regions request
  needs. Those receptions were previously skipped because the packet carries no pubkey,
  but that was never the real obstacle: the discover path has the same gap and closes it
  with a CoreScope lookup, using the very same prefixes the app already resolves to show
  names.

  This fills a specific hole. The discover sweep backs off for 15 seconds after any
  organic reception, so in busy areas — where forwarder traffic is densest — it is
  suppressed and yields the fewest candidates exactly where there is the most to hear.

- **The log header reports whether resolving those prefixes actually works.** New row:
  `path keys  12 of 15 path-hash prefixes resolved to a pubkey (3 ambiguous or unknown)`.
  It counts distinct prefixes, not lookups, and sits in the header rather than in a log
  line because the 200-line ring buffer rolls per-prefix lines out long before a drive
  ends. This is the number that decides whether the forwarder source earns its airtime.

- **Two scheduling invariants that were documented but not enforced.** The shared
  one-ask-per-60s airtime budget is now stamped at the single site that transmits, so it
  counts asks from both the timer and the heard path; previously timer asks spent
  airtime without consuming the budget. And the timer no longer asks over a live
  request — doing so overwrote the pending tag, after which the real reply was rejected
  as a mismatch, so the fallback path was discarding the answers this feature collects.

- **An answered repeater is no longer re-asked after being heard again.** The candidate
  map value doubles as the answered-key. Advert-sourced candidates carry a real
  timestamp while discover- and forwarder-sourced ones carry none, and writing the
  latter over the former made a repeater that had already answered read as due. This
  affected the discover path before this release.

## Upgrade notes

- **Service-worker cache bumped to `coredrive-rx-v41`.** Clients pick up the new bundle
  on their next load with a connection.
- **No MQTT contract change.** No new field and no new topic, so no ingestor work is
  needed to accept this release. The `regions` record shape is unchanged.
- **No config change.** `regionDiscovery` keeps its existing default; nothing new to set.
- **Expect more region requests per drive, not more airtime.** The ceiling is still one
  ask per 60 seconds shared across both paths. What changes is which repeater that ask
  is aimed at — one currently in range instead of one a clock chose.
- **Forwarder candidates depend on `resolveUrl`.** With no resolve endpoint configured,
  or no data connection, a path-hash prefix cannot become a candidate. A lookup that
  fails at the HTTP level is cached for the session, so a repeater can be locked out by
  a transient server error until the next session; the new `path keys` row is how that
  becomes visible.
- **Node type is unknown for a forwarder.** A path hash carries none, so a room server
  that forwards but does not implement the regions reply may be asked once and then held
  off by the normal retry backoff. Companions and sensors do not forward and so do not
  appear here.
- Bundle 443.39 kB to 443.94 kB, gzip 139.94 to 140.12.
- Tests: 276 pass (+10).
